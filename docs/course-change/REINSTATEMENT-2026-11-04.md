# ข้อมูลเพิ่มเติม 4/11 — ลืมชำระค่าเทอม

รับข้อมูลวันที่ 4 พฤศจิกายน 2569 จากข้อความที่ผู้ใช้ส่งในแชต

**ขอบเขตยืนยันแล้ว: พัฒนาเฉพาะลด/ถอนรายวิชา ไม่เพิ่มคำร้องคืนสถานภาพ ลงทะเบียนสาย หรือชำระค่าเทอม**

ผู้ใช้ยืนยันให้อ่านข้อมูลจากผู้ปฏิบัติงานทั้งหมดเพื่อคัดเงื่อนไขที่อาจกระทบลด/ถอน หากไม่มีความเกี่ยวข้องให้เก็บเป็นข้อมูลอ้างอิง ไม่ขยายขอบเขตฟีเจอร์

กรณีนี้เป็นการขอคืนสถานภาพนิสิตและลงทะเบียนเรียนสายหลังกำหนด เนื่องจากไม่ได้ชำระค่าเล่าเรียนภายในเวลาที่มหาวิทยาลัยกำหนด แยกจากการลด/ถอนรายวิชา ข้อมูลชุดนี้ไม่ได้ยืนยันกฎถอนรายวิชา Block หรือวิชาเลือกที่ยังค้างอยู่

## การตรวจแหล่งข้อมูล

เปิดทั้งสองลิงก์แบบอ่านอย่างเดียววันที่ 4/11/2569 ทั้งคู่แสดง “ต้องมีสิทธิ์เข้าถึง” จึงยังตรวจชื่อแบบฟอร์ม ช่องกรอก เงื่อนไขไฟล์ หรือข้อความยืนยันหลังส่งไม่ได้ ไม่ได้ยื่นคำร้อง ขอสิทธิ์ หรือเปลี่ยนบัญชี

ขั้นตอนในเอกสารนี้จึงอ้างอิงข้อความที่ผู้ใช้ให้มา ไม่ใช่ผลการตรวจแบบฟอร์มภายในหรือการยืนยันระเบียบจากมหาวิทยาลัยโดยตรง

## ผลกระทบต่อการลด/ถอนที่ยังต้องตรวจ

ข้อความที่ได้รับอธิบายวิธีขอคืนสถานภาพ แต่ไม่ได้ระบุว่าการค้างชำระ การพ้นสถานภาพ หรือการรอคืนสถานภาพเปลี่ยนสิทธิลด/ถอนอย่างไร จึงยังสรุปไม่ได้ทั้งว่า “เกี่ยวข้องแน่นอน” หรือ “ไม่มีผล” และยังไม่เพิ่มกฎปิดกั้นคำร้องจากข้อมูลชุดนี้

| ประเด็น | เหตุผล / งานที่ทำต่อได้เมื่อได้คำตอบ |
| --- | --- |
| ค้างค่าเทอม/พ้นสถานภาพ/รอคืนสถานภาพ มีผลต่อสิทธิ์ยื่นลดหรือถอนต่างกันหรือไม่? | หากมีผลจริง จึงเพิ่มการตรวจสิทธิ์และข้อความแนะนำให้ตรงกฎ ไม่ใช้การค้างชำระแทนสถานภาพโดยอัตโนมัติ |
| ระหว่างรอคืนสถานภาพ รายวิชาถือว่าลงทะเบียนอยู่หรือยัง และแหล่งข้อมูลใดเป็นตัวตัดสิน? | กำหนดความหมายของรายวิชาที่แสดงและสิทธิ์เลือกวิชา ไม่ถือว่ามีแถว enrollment ในเดโมเป็นหลักฐานยืนยันสิทธิ์จริง |
| หากรอคืนสถานภาพจนเลยกำหนดลด/ถอน มีกฎเฉพาะหรือไม่? | ตั้งเส้นทาง/คำแนะนำตามกฎที่ยืนยัน ห้ามต่อเวลา เปลี่ยนสัปดาห์ หรือสร้างข้อยกเว้นเอง |
| หากสถานภาพเปลี่ยนหลังยื่นลด/ถอนไปแล้ว ต้องจัดการคำร้องที่ค้างอย่างไร? | กำหนดจุดตรวจซ้ำและผู้รับผิดชอบก่อนดำเนินการต่อ โดยไม่ยกเลิกคำร้องเดิมเอง |

คำถามเริ่มต้นที่สั้นที่สุดสำหรับผู้ปฏิบัติงาน: “กรณีค้างค่าเทอมหรืออยู่ระหว่างขอคืนสถานภาพ มีผลต่อสิทธิ์หรือกำหนดเวลาลด/ถอนรายวิชาไหมคะ?” หากยืนยันว่าไม่มีผล ไม่ต้องขยายไปถามรายละเอียดการคืนสถานภาพ หากมีผลจึงขอเงื่อนไขและแหล่งข้อมูลที่เกี่ยวข้องเฉพาะจุด

## สิ่งที่ตรวจพบในเดโมปัจจุบัน

ตรวจโค้ด `eligibleCourses` และ `submitRequest` ใน `prototype-1/backend/src/modules/course-change/service.ts` พร้อมแบบจำลอง User/Enrollment วันที่ 4/11/2569:

- ตรวจรายวิชาที่ลงทะเบียน ภาคการศึกษา ช่วงเวลาที่เปิด รายวิชาที่หลักสูตรอนุญาต สถานะเปิดใช้งานรายวิชา และคำร้องเดิม
- ยังไม่มีการตรวจสถานะชำระค่าเทอมหรือสถานภาพนิสิตทางทะเบียนในเส้นทางลด/ถอน
- `User.isActive` เป็นสถานะบัญชีในแอป ไม่ควรนำไปตีความแทนสถานภาพนิสิตทางทะเบียน
- ข้อเท็จจริงนี้บอกขอบเขตโค้ดปัจจุบัน ไม่ใช่การยืนยันว่ากฎจริงอนุญาตหรือไม่อนุญาต

## ข้อมูลนอกขอบเขตที่เก็บไว้เพื่ออ้างอิง

ต้นฉบับระบุ CR34 แต่ชื่อไฟล์ขึ้นต้น CR41 ยังไม่ทราบเหตุผล เก็บความคลาดเคลื่อนไว้โดยไม่แก้เอง ไม่ใช่ประเด็นที่ต้องรอคำตอบเพื่อพัฒนางานลด/ถอนต่อ

การสร้าง/รับ/ลงนาม PDF คืนสถานภาพ สายอนุมัติคืนสถานภาพ การเก็บเงิน และการยืนยันผลคืนสถานภาพอยู่นอกงานนี้ ไม่เพิ่มเมนู ฟอร์ม API หรือฐานข้อมูลเพื่อรองรับ

ข้อมูลชุดนี้ไม่ได้ระบุการรวมคำร้องสองฉบับหรือส่ง PI จึงไม่ใช้แทนรายละเอียดเอกสารของงานถอน

## งานที่ทำรอบนี้

- บันทึกข้อมูลต้นฉบับและผลคัดกรองความเกี่ยวข้องกับลด/ถอนตามขอบเขตที่ผู้ใช้ยืนยัน
- เชื่อมเอกสารนี้จากรายงาน rport 28/10 โดยคงวันที่และผลตรวจเดิมไว้
- ตรวจโค้ดสิทธิ์ลด/ถอน ไม่เพิ่มกฎค่าเทอมที่ยังไม่มีข้อมูลยืนยัน
- ปรับหน้านิสิตเมื่อไม่พบรายวิชา: ระบุว่าเป็นข้อมูลที่ยังไม่พบ ไม่สรุปว่าไม่มีสิทธิ์ลด/ถอน แนะนำติดต่อเจ้าหน้าที่หลักสูตรหากลงทะเบียนแล้ว และเพิ่มปุ่มโหลดรายวิชาอีกครั้งพร้อมสถานะกำลังโหลด การโหลดนี้อ่านข้อมูลเท่านั้น ไม่ยื่นคำร้อง
- ตรวจวันที่ 4/11/2569: frontend `npm run build` ผ่านทั้ง TypeScript และ Vite; `git diff --check` ผ่าน ยังไม่ได้ทดสอบหน้าจอกรณีนี้ผ่านเบราว์เซอร์
