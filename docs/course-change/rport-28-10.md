## ข้อมูลผู้ใช้งานจริงที่ได้รับ

พี่นัทเป็นเจ้าหน้าที่ผู้ดำเนินงานปัจจุบัน ยังไม่ได้ทดลอง demo และแจ้งว่าจุดยากคือถอนช่วงต้นเทอมและวิชาเลือกภาคปลาย

- วิชา Block สัปดาห์ 1–7: ยื่นคำร้องหลักสูตรในสัปดาห์ 6 → เจ้าหน้าที่รวบรวมให้อาจารย์ลงนาม → ส่งคืนให้นิสิตสัปดาห์ 7 → นิสิตทำรายการ Reg Chula → รวมคำร้องสองฉบับ → ส่ง PI โดยมี Outlook แจ้งขั้นตอน
- วิชาเลือกภาคปลายมีครึ่งเทอมแรก ครึ่งเทอมหลัง และเต็มเทอม รายละเอียดยังรอพี่นัทสรุป
- ข้อมูลนี้ไม่ใช่การยืนยันว่า withdrawal ทุกวิชาในสัปดาห์ 3–6 ใช้ flow เดียวกัน

## งานรอบนี้

ทำส่วนปรับประสบการณ์ใช้งานและการรวบรวมคำร้องเสร็จในเดโมแล้ว ระบบยังไม่พร้อมใช้แทนขั้นตอนทะเบียนจริง เพราะกฎรายรูปแบบวิชา เอกสาร ผู้ลงนาม และการเชื่อมต่อภายนอกยังไม่ยืนยัน

### ฝั่งนิสิต

- แยก “ยื่นคำร้องใหม่” กับ “ติดตามคำร้อง” ลดข้อมูลที่ต้องอ่านในหน้าเดียว ข้อมูลฟอร์มยังอยู่เมื่อสลับสองมุมมองภายในหน้า
- ยื่นตามลำดับ เลือกประเภท → เลือกรายวิชา → ระบุเหตุผล → ตรวจข้อมูลและเส้นทางล่าสุด → ยืนยัน → ติดตามผล
- เพิ่มค้นหารายวิชา ล้างคำค้น และข้อความเมื่อไม่พบรายการ วิชาที่เลือกยังแสดงชัดเจนแม้คำค้นไม่ตรงกับวิชานั้น
- รายวิชาที่ทำรายการไม่ได้บอกเหตุผล และยังเข้าถึงด้วยคีย์บอร์ดเพื่ออ่านเหตุผลได้ ป้องกันการกดด้วยตัวตรวจสิทธิ์เดิม
- หน้าตรวจทานแสดงวิชา เหตุผล เส้นทาง และข้อความว่าการยื่นยังไม่ใช่ผลทะเบียนสุดท้าย ป้องกันการส่งซ้ำระหว่างกำลังทำรายการ
- แสดงข้อผิดพลาดในหน้า รักษาข้อมูลที่กรอกเมื่อเชื่อมต่อไม่ได้ และลองตรวจใหม่ได้ เพิ่มฉบับร่างในแท็บเดิมแยกบัญชี/เทอม เรียกคืนได้ภายใน 24 ชั่วโมง หากเก็บฉบับร่างไม่ได้จะแจ้งเตือนและเตือนก่อนปิด/รีโหลด ไม่ใช่ฉบับร่างบนเซิร์ฟเวอร์หรือการกู้คืนข้ามอุปกรณ์
- แจ้งเตือนเปิดคำร้องที่ตรงกันได้โดยตรง แต่ละสถานะบอกผู้รับผิดชอบ/ขั้นตอนถัดไป พร้อมค้นหา กรองสถานะ และอัปเดตข้อมูลได้เอง

### ฝั่งเจ้าหน้าที่

- เพิ่มตัวกรองรวมคำร้องตามรายวิชาและภาคการศึกษา พร้อมจำนวนจากข้อมูลทั้งหมดที่ตรงเงื่อนไข ไม่ได้นับเฉพาะหน้าแรก
- เลือกคำร้องที่รอพิจารณาในหน้าปัจจุบัน ล้างที่เลือก และตรวจรายการในหน้าต่างยืนยันก่อนอนุมัติแบบกลุ่ม การเลือกถูกล้างเมื่อเปลี่ยนหน้า/ตัวกรอง
- ส่งออก CSV สรุปเฉพาะรายการที่เลือก ใช้ UTF-8 BOM เปิดภาษาไทยได้ และป้องกันข้อความถูกตีความเป็นสูตรในตารางคำนวณ ไฟล์นี้ช่วยตรวจงาน ไม่ใช่เอกสารคำร้องทางการหรือไฟล์ส่ง PI
- หน้ารายละเอียดบอกสถานะ ขั้นตอนถัดไป เหตุผล ประวัติ และผลการทำรายการ จัดข้อมูลอ้างอิงทางเทคนิคไว้ในส่วนที่กดเปิดอ่านได้
- ปรับยืนยัน/สถานะระหว่างบันทึกของการอนุมัติ ไม่อนุมัติ บันทึกผล และตั้งค่า ให้ข้อความสอดคล้องกัน สิทธิ์เจ้าหน้าที่ยังใช้บทบาท staff เดิม รอแยกบทบาทตามข้อมูลผู้ปฏิบัติงานจริง

### รายละเอียดร่วม

- ปรับภาษาไทย ลำดับข้อมูล ระยะห่าง พื้นผิว focus และ pressed state ให้สอดคล้องกับดีไซน์ขาวดำเดิมของระบบ
- หน้าต่างมีปุ่มปิดชื่อชัดเจน รองรับ Escape และ footer ติดด้านล่างระหว่างเลื่อน พร้อมปิดการกดซ้ำขณะบันทึก
- ใช้ transition สั้นประมาณ 150–200 ms และเปิด/ปิดหน้าต่าง 180/120 ms รองรับ reduced motion ทั้ง animation และการเลื่อนไปยังรายละเอียดบนมือถือ
- มีสถานะโหลด ไม่มีข้อมูล โหลดไม่สำเร็จ ลองอีกครั้ง เวลาอัปเดตล่าสุด และ toast ที่ปิดได้ ไม่แสดงข้อความว่างหรือเลข 0 แทนค่าที่กำลังโหลด
- แยกโหลดหน้าลด/ถอน หน้าจอง และหน้าข้อมูลหลักเมื่อใช้งาน พร้อมหน้ารอและข้อความกู้คืนเมื่อโหลดหน้าไม่ได้

## งานเพิ่มเติมที่ลงมือทำต่อทันที

1. **ฉบับร่าง:** เก็บประเภท วิชา เหตุผล และรหัสการยื่นใน sessionStorage แยกตามบัญชี/เทอม มีป้ายกู้คืนและยืนยันก่อนล้าง ล้างหลังยื่นสำเร็จ/ล้างเอง/ออกจากระบบ การปิดแท็บอาจทำให้ฉบับร่างหายตามวงจร sessionStorage ของเบราว์เซอร์ จึงระบุขอบเขตนี้ในหน้าจอ
2. **ตรวจผลก่อนยื่นซ้ำ:** บันทึก clientRequestId ลงฐานข้อมูลพร้อม unique index ใช้ transaction lock สำหรับคำขอพร้อมกัน การลองยื่นข้อมูลเดิมได้คำร้องเดิม แม้หมดเขตหรือคำร้องถูกยกเลิกแล้ว การเปลี่ยนเนื้อหาโดยใช้รหัสเดิมถูกปฏิเสธ และคำร้องใหม่ยังตรวจสิทธิ์/เวลาเหมือนเดิม
3. **การกู้คืนฝั่งนิสิต:** เมื่อยืนยันแล้วยังไม่ทราบผล มีปุ่ม “ตรวจสอบผลการยื่น” แบบอ่านอย่างเดียว ค้นเฉพาะคำร้องของบัญชีนั้น ไม่สร้างคำร้องใหม่ ถ้าไม่พบจึงกลับไปตรวจข้อมูลและยืนยันเองได้ ไม่มีการส่งอัตโนมัติหลังกลับมาออนไลน์
4. **ประกาศรายวิชา:** ส่งหมายเหตุหลักสูตรถึงหน้านิสิตแม้รายวิชานั้นยังยื่นได้ แสดงทั้งบนการ์ดและหน้าตรวจทาน และโหลดทั้งช่วงเวลา/สิทธิ์/ประกาศใหม่ก่อนให้ยืนยัน
5. **ออกจากระบบ/ระบบล่ม:** แก้ session cache ที่เคยแสดงบัญชีเก่าหลัง logout และใช้วิธีเดียวกันเมื่อ session หมดอายุ ออกจากระบบไม่สำเร็จจะแจ้งให้ลองใหม่ หากเปิดเว็บตอน API ขัดข้องจะแสดงหน้าลองเชื่อมต่อแทนการเข้าใจว่าไม่ได้ล็อกอิน โดยไม่ล้างฉบับร่าง
6. **การตรวจซ้ำ:** เพิ่ม `npm run test:fresh` สร้างฐานทดสอบใหม่เฉพาะรอบ migrate/seed/run แล้วลบเฉพาะฐานนั้น ป้องกัน fixture ที่ถูกใช้ไปแล้ว ทำให้ตรวจทั้งระบบซ้ำได้โดยไม่รีเซ็ตเดโม
7. **แพ็กเกจและการโหลด:** อัปเดต Vite/React plugin/Router/Zod/resolver/Vitest/CSV และแพตช์ที่เกี่ยวข้อง ปัก deepmerge-ts 8 สำหรับ Prisma config เพื่อแก้รายการ advisory โดยไม่ย้าย Prisma ทั้งระบบ ทั้ง generate, migrations, tests และ build ผ่าน แยก React vendor ออกจาก main chunk ไม่เพิ่มเกณฑ์ warning เพื่อซ่อนปัญหา
8. **พร้อมให้คนทดลอง:** จัดทำ [คู่มือ UAT 28/10](UAT-28-10.md) มีงานฝั่งนิสิต/เจ้าหน้าที่ เกณฑ์สังเกต และตารางจดผล ยังไม่มีการอ้างว่าพี่นัททดลองหรือยืนยันแล้ว
9. **พร้อมคุย Product Owner:** จัดทำ [สคริปต์เดโมและข้อเสนอ requirement](PO-DEMO-28-10.md) แยกความสามารถปัจจุบัน ส่วนจำลอง งานที่ยังไม่ทำ และ flow เอกสารที่ทีมควรเสนอเองเพื่อให้ยืนยัน

เพิ่ม migration `20261028120000_course_change_submission_retry` และใช้กับฐานเดโมแล้ว เป็นการเพิ่ม nullable column/index จึงเก็บคำร้องเดิมไว้ทั้งหมด

## Flow ที่เดโมรองรับในตอนนี้

เดโมยังใช้ routing matrix ระดับภาคการศึกษาเดิม: A จำลองส่ง Reg Chula, B อาจารย์อนุมัติแล้วสร้างเอกสารตัวอย่าง/จำลองส่ง Reg Chula และ PI, C หลักสูตรอนุมัติแล้วบันทึกขั้นตอนส่ง สนท. เส้นทางและข้อมูลช่วงเวลาของคำร้องถูกเก็บไว้ ไม่เปลี่ยนตามการตั้งค่าใหม่ย้อนหลัง

**ยังไม่มี workflow คืนคำร้องที่ลงนามในสัปดาห์ 7 → ให้นิสิตทำ Reg Chula → รับไฟล์ฉบับที่สอง → รวม → ยืนยันส่ง PI ตามข้อมูลพี่นัท** และยังไม่มีปฏิทินราย Block/ครึ่งเทอม รายการเหล่านี้ต้องเพิ่มหลังยืนยันกฎ ไม่ถือว่าป้ายแจ้งเตือนในหน้าเว็บทำให้ flow ครบแล้ว

ไฟล์เอกสารที่ระบบสร้างในปัจจุบันเป็น HTML ตัวอย่างพร้อม hash เท่านั้น ไม่ใช่ PDF ทางการ ลายเซ็นดิจิทัลที่หน่วยงานรับรอง หรือการส่งข้อมูลสำเร็จใน Reg Chula/PI จริง

## สิ่งที่ยังทำให้สมบูรณ์ไม่ได้

### ใครต้องให้ข้อมูล และอะไรยังทำต่อเองได้

สถานะที่พูดได้วันนี้คือ **เดโมส่วนที่พัฒนารอบนี้ผ่านการตรวจและพร้อมให้ผู้ใช้งานทดลอง** ไม่ใช่ “ระบบจริงเสร็จแล้ว รอแค่พี่นัท” การทดสอบ 115 ข้อเป็นหลักฐานของขอบเขตที่ทดสอบ ไม่ใช่การรับรอง flow จริงทุกกรณี

| เรื่องค้าง | แหล่งข้อมูล/ผู้ร่วมยืนยัน | สิ่งที่ทีมพัฒนายังทำเองได้ |
|---|---|---|
| รูปแบบวิชา ช่วงเวลา ผู้ลงนาม เอกสาร และเกณฑ์จบงาน | พี่นัทและผู้ยืนยันนโยบายของหลักสูตร | เตรียมตารางกรณีและชุดทดลองไว้แล้ว; การตั้งค่ากฎจริงและต่อ flow เฉพาะต้องรอคำตอบ |
| SSO, ข้อมูลลงทะเบียน, Reg Chula และ PI | ผู้ดูแลระบบของมหาวิทยาลัย/ทะเบียน/คณะ ต้องระบุผู้ประสานงานและสิทธิ์ทดสอบ; พี่นัทอาจช่วยประสาน | ทำรายการข้อมูลที่ต้องแลกเปลี่ยนและออกแบบการรับมือ error ได้; ยังเขียน client จริงหรือยืนยันความเข้ากันได้จาก API ที่ไม่มี contract ไม่ได้ |
| คิวส่งข้อมูลภายนอก การลองส่งใหม่ และผลส่งไม่สำเร็จ | ทีมพัฒนาทำโครงสร้างได้เอง; กฎตอบสนองต่อผลทะเบียนจริงต้องยืนยันกับหลักสูตรและปลายทาง | **ยังไม่ทำ:** ย้ายการส่งออกจาก DB transaction เป็น outbox/worker และทดสอบการส่งซ้ำ/timeout/ส่งสำเร็จแต่ไม่ได้รับคำตอบด้วย adapter ทดสอบ งานนี้ไม่จำเป็นต้องรอพี่นัททั้งหมด |
| การปล่อยระบบ การสำรอง/กู้คืน การติดตามข้อผิดพลาด และการทดสอบบนระบบติดตั้งจริง | ทีมพัฒนาและผู้ดูแลโครงสร้างพื้นฐานของโครงการ | **ยังไม่ทำครบ:** เตรียมและซ้อมขั้นตอนติดตั้ง/กู้คืนและตรวจสภาพแวดล้อมได้เอง; การใช้งานจริงยังต้องมีเครื่อง/สิทธิ์และการตั้งค่าของโครงการ |
| การตรวจความเข้ากันได้และการใช้งานจริง | ทีมพัฒนา พี่นัท และนิสิตผู้ทดลอง | มี responsive/browser checks ตามรายงานแล้ว; ยังไม่ใช่การทดสอบครบทุกเบราว์เซอร์ เครื่องจริง หรือ screen reader และยังไม่มีผล UAT จากพี่นัท |

งานเทคนิคที่ระบุว่า “ยังไม่ทำ” ข้างต้นเป็นงานเตรียมใช้งานจริงที่ทำต่อได้ ไม่ได้ถูกนับรวมเป็นงานเสร็จในรอบนี้ เมื่อได้คำตอบพี่นัทแล้ว ยังต้องพัฒนาและทดสอบ flow ที่ยืนยันเพิ่มเติม ไม่ใช่แค่ใส่ข้อมูลแล้วพร้อมใช้ทันที

| สิ่งที่รอ | เหตุผลที่ต้องรอ | ข้อมูลที่ต้องได้ |
|---|---|---|
| นโยบายรายรูปแบบวิชา | เวลาและเส้นทางไม่เหมือนกัน การใช้สัปดาห์เทอมอย่างเดียวไม่พอ | กฎครึ่งเทอมแรก/หลัง/เต็มเทอม และ Block รวมถึงรายวิชาที่เข้าข่ายแต่ละเทอม |
| วันตัดรอบ | ยังทราบแค่สัปดาห์ 6/7 ของกรณี Block | วัน เวลา เขตเวลา ข้อยกเว้น และหลักการนับสัปดาห์ |
| ผู้ลงนาม/สิทธิ์แทน | ไม่ทราบลำดับและผู้รับผิดชอบครบ | รายชื่อบทบาท ลำดับอนุมัติ วิธีมอบหมาย และวิธีลงนามที่รับได้ |
| คำร้องสองฉบับ | ยังไม่ทราบฟิลด์ แบบล่าสุด และแหล่งออกเอกสารแต่ละฉบับ | ตัวอย่างที่ปิดข้อมูลส่วนตัว แบบฟอร์มเปล่า และข้อความ Outlook |
| คืนเอกสารและหลักฐานปลายทาง | ต้องแยกว่าอัปโหลดไฟล์ ส่งคืน ทำ Reg Chula ส่ง PI และจบจริงอย่างไร | เอกสารที่เจ้าหน้าที่คืน สิ่งที่นิสิตต้องส่งกลับ และหลักฐานยืนยันผล |
| ผลทะเบียนไม่ผ่าน/แก้ไข/ยื่นใหม่ | ยังไม่ทราบ transition และผลต่อสิทธิ์ | ขั้นตอนเมื่อไม่ผ่าน เอกสารขาด ยกเลิก หรือแก้ข้อมูล |
| ระบบมหาวิทยาลัยจริง | ยังไม่มี API contract/สิทธิ์ทดสอบ | ผู้ประสานงาน Chula SSO, enrollment, Reg Chula, PI และ LINE |
| การรับรองเอกสารจริง | HTML/hash ปัจจุบันเป็นตัวอย่าง | Template และข้อกำหนด PDF/ลายเซ็นจากผู้รับเอกสาร |
| การตรวจรับกับผู้ใช้จริง | การตรวจโดยผู้พัฒนาไม่ใช่ usability test | ให้พี่นัทและนิสิตทดลองงานจริงพร้อมเกณฑ์สำเร็จ |

คำร้องสองฉบับจะใช้ยืนยันแหล่งเอกสาร ฟิลด์ ผู้ลงนาม และลำดับรวมไฟล์ ก่อนเลือกว่าสร้างอัตโนมัติ รับไฟล์จาก Reg Chula หรือเติมข้อมูลส่วนใดได้ ตัวอย่างไม่ใช่สิทธิ์ให้สร้างเอกสารทางการแทนระบบต้นทาง

### ลำดับงานหลังได้ข้อมูล

1. แปลงคำตอบพี่นัทเป็นตาราง “รูปแบบวิชา × ช่วงเวลา × ผู้ทำขั้นตอน × เอกสาร × เกณฑ์จบ” และให้ยืนยันความเข้าใจ
2. เพิ่มปฏิทินรายวิชา/Block และสถานะส่งคืนเอกสาร รอนิสิตทำ Reg Chula รอรวมเอกสาร/ส่ง PI พร้อมสิทธิ์และหลักฐานที่ได้รับการยืนยัน
3. ทำ PDF/การรวมไฟล์/ลายเซ็นตามแบบจริง และเชื่อมระบบเฉพาะที่มีสิทธิ์และช่องทางรองรับ
4. ให้พี่นัทและนิสิตทดสอบกรณีสำเร็จ เอกสารขาด ไม่อนุมัติ หมดเขต และปลายทางไม่ผ่าน ก่อนสรุปว่าพร้อมใช้งานจริง
