# ลด/ถอน — ข้อมูลผู้ปฏิบัติงานเพิ่มเติม 4/11/2569

> หลังจัดทำแผนนี้ได้พัฒนา flow รุ่นใหม่แล้ว ดู [ความสามารถที่ทำแล้ว ผลตรวจ และงานที่ยังเหลือ](IMPLEMENTATION-2026-11-04.md) รายการช่องว่าง/แผนด้านล่างเป็นบันทึกก่อนลงมือ ไม่ใช่สถานะโค้ดล่าสุด

ที่มา: ข้อความรายละเอียดที่ผู้ใช้ส่งวันที่ 4 พฤศจิกายน 2569 ใช้เป็นข้อมูลกระบวนการจากผู้ปฏิบัติงาน ไม่ใช่การยืนยันระเบียบมหาวิทยาลัยจากแหล่งทางการอีกครั้ง

**ขอบเขต: ลด/ถอนรายวิชาเท่านั้น** ข้อมูลคืนสถานภาพ ค่าเทอม และ จท41 เก็บไว้คัดผลกระทบต่อสิทธิ์/ข้อมูลรายวิชา ไม่เพิ่มประเภทคำร้องเหล่านั้น

เอกสารนี้ปรับความเข้าใจจากข้อมูลใหม่ ไม่ได้หมายความว่าความสามารถที่ระบุด้านล่างถูกพัฒนาแล้ว และไม่เปลี่ยนคำร้องเดิมในฐานข้อมูล

## กฎและข้อเท็จจริงที่ได้รับเพิ่ม

- มหาวิทยาลัย: ลดในสัปดาห์ภาคการศึกษา 1–6 ถอนในสัปดาห์ภาคการศึกษา 7–12
- หลักสูตร: ลดภายใน 1 ใน 3 ของ Block ถอนก่อนสอบ Final 1 สัปดาห์
- ต้องพิจารณาทั้งปฏิทินภาคการศึกษาและกำหนดของรายวิชา ไม่ใช้สัปดาห์ปัจจุบันของเทอมเลือกเส้นทางเพียงอย่างเดียว
- ทุกเส้นทางที่ระบุมีขั้นตอนเจ้าหน้าที่ตรวจคำร้องก่อนดำเนินการต่อ การตรวจนี้ไม่ใช่การอนุมัติของอาจารย์หรือผลทะเบียน
- ผู้ลงนาม/อนุมัติเป็นอาจารย์หรือผู้เกี่ยวข้องตามกรณี ข้อมูลไม่ได้ยืนยันว่าทุกกรณีคืออาจารย์ที่ปรึกษา
- “รายวิชาเต็มภาคการศึกษา (สัปดาห์ 1–18)” บอกระยะเวลาเรียน ไม่ใช่หลักฐานว่าเปิดลดหรือถอนตลอดสัปดาห์ 1–18
- กำหนดการประกาศราย Block และการติดตามเอกสารเป็นงานหลักของเจ้าหน้าที่ ไม่ใช่เพียงรับแล้วกดอนุมัติ

## ระบบปัจจุบันต่างจากข้อมูลใหม่ตรงไหน

ตรวจโค้ดวันที่ 4/11/2569:

1. `backend/src/modules/course-change/service.ts`: เส้นทาง `reg_direct` สร้างคำร้องสถานะ processing และเรียก mock Reg Chula ทันที ข้ามเจ้าหน้าที่ตรวจ ซึ่งไม่ตรงข้อมูลใหม่
2. `backend/src/modules/course-change/timeline.ts`: ใช้ flow A/B/C และ event เส้นทางเดิม ยังไม่มีขั้นตรวจเจ้าหน้าที่/ส่งแก้ไข/รอลงนาม/คืนเอกสาร/รอนิสิตทำภายนอกแยกกัน
3. `backend/src/modules/course-change/settings.ts` และ `frontend/src/features/course-change/SettingsView.tsx`: ตั้งช่วงระดับเทอมและเปิดสิทธิ์รายวิชา ยังไม่มีปฏิทิน Block/Final/กำหนดรายตอนเรียน
4. `backend/prisma/schema.prisma`: Enrollment มี Section เป็นข้อมูลประกอบ แต่กฎรายวิชาใช้คู่ term/course ยังไม่ได้แยก offering/Section ที่อาจมีรูปแบบและวันสอบต่างกัน
5. หน้ารายละเอียดมีเอกสาร HTML ตัวอย่าง ไม่ใช่ระบบรับไฟล์ลงนาม ส่งคืน ตรวจฉบับแก้ไข หรือรวม PDF จริง
6. การ approve ในเดโมอาจเรียก mock Reg/PI และสร้างตัวอย่างทันที ยังไม่ใช่ขั้นงานที่เจ้าหน้าที่และนิสิตทำตามกระบวนการใหม่
7. completed เป็นเจ้าหน้าที่บันทึกเอง ยังไม่มีการแยกผล “เอกสารครบ” กับ “ทะเบียนดำเนินการแล้ว” ตามหลักฐานจริง

## งานที่มีข้อมูลพอเริ่มพัฒนาได้

รายการต่อไปนี้เป็น backlog ที่ลงรายละเอียดได้แล้ว ยังไม่ได้แก้โค้ดในรอบบันทึกข้อมูลนี้:

| ลำดับ | งาน | พฤติกรรมที่ควรได้ |
| --- | --- | --- |
| 1 | แยกเจ้าหน้าที่ตรวจคำร้องจากการอนุมัติ | คำร้องใหม่เข้าสู่คิวตรวจความครบถ้วน ตรวจวิชา/Section/รูปแบบ/กำหนดการ มีส่งแก้ไขพร้อมเหตุผลและยื่นฉบับแก้ไขในคำร้องเดิม กดตรวจผ่านไม่เท่ากับอาจารย์ลงนามหรือทะเบียนสำเร็จ |
| 2 | ตั้งปฏิทินต่อรอบวิชา/Section | ระบุ Block หรือเต็มภาค วันเรียน/วันสอบเมื่อทราบ กำหนดเปิด–ปิดรับจริง และเส้นทางโดยผู้ตั้งค่าที่ได้รับสิทธิ์ แสดงวันประกาศชัดเจน รองรับต่างกันในวิชาเดียวคนละตอน |
| 3 | งานรวบรวมและติดตามผู้ลงนาม | รวมตามเทอม/วิชา/Section/Block/รอบ ลงรายการผู้รับผิดชอบ บันทึกส่งขอลงนามและรับคืน ไม่สร้างลายเซ็นแทนอาจารย์จากปุ่มอนุมัติ |
| 4 | รับและคืนเอกสารในคำร้องเดิม | เจ้าหน้าที่แนบฉบับลงนามให้เจ้าของคำร้องดาวน์โหลดได้ บันทึกรุ่นเอกสาร/ผู้ส่ง/เวลา และขอแก้ไขได้ จำกัดสิทธิ์ไฟล์เฉพาะผู้เกี่ยวข้อง การใช้เว็บแทน Outlook เป็นข้อเสนอผลิตภัณฑ์ ต้องทดลองกับผู้ปฏิบัติงาน |
| 5 | รายการงานของนิสิตที่ตรงเส้นทาง | บอกว่าต้องทำ Reg Chula, PI หรือรอหลักสูตรส่ง สนท. พร้อมกำหนดและวิธีบันทึกหลักฐาน ไม่แสดงให้ทุกกรณีทำเหมือนกัน และไม่แสดงข้อความว่าส่งภายนอกแล้วจากเพียงการกดในเว็บ |
| 6 | ช่วยรวม PDF ในกรณีที่ยืนยันว่าต้องรวม 2 ฉบับ | รับไฟล์ PDF ที่มีอยู่จริง ให้เลือกฉบับ/ลำดับ ตรวจว่าอ่านได้และให้ดูตัวอย่าง/ดาวน์โหลด เก็บต้นฉบับ ไม่ต้องรอ template ทางการเพื่อเริ่มส่วนรวมไฟล์ แต่ต้องยืนยันชื่อและองค์ประกอบเอกสารก่อนเปิดใช้จริง |
| 7 | คิวติดตามงานเจ้าหน้าที่ | แยกงานต้องตรวจ งานรอลงนาม งานรอนิสิต งานต้องแก้เอกสาร งานพร้อมรวบรวมส่ง สนท. และงานรอผล ผู้ใช้เห็นผู้ทำขั้นถัดไปและเวลาค้าง ไม่เพิ่มการส่ง Outlook/LINE จริงโดยไม่มีช่องทางเชื่อมต่อ |
| 8 | แยกเอกสารครบ/ส่งแล้ว/ผลทะเบียน | แต่ละเหตุการณ์มีผู้บันทึก เวลา หมายเหตุ และหลักฐานตามเกณฑ์ที่ตกลง ให้เจ้าหน้าที่ระบุผลด้วยมือได้อย่างตรงไปตรงมาระหว่างยังไม่เชื่อม API ไม่ถือว่า PI รับไฟล์แล้วแปลว่าถอนสำเร็จ |

เริ่มด้วยการตั้งวันเปิด–ปิดที่หลักสูตรประกาศจริงได้ โดยยังไม่คำนวณสูตร 1/3 หรือ Final อัตโนมัติเมื่อกติกาปัดเศษ/วันตัดรอบยังไม่ชัด หากยังไม่มีวันที่ยืนยัน ให้คงรอบนั้นเป็นฉบับร่าง ไม่เปิดรับจากวันที่คาดเดา

การเปลี่ยน workflow ต้องเพิ่มรุ่นกฎ/เส้นทางและรักษาประวัติคำร้องเก่า ไม่ย้ายคำร้องเดิมไปขั้นใหม่เงียบ ๆ ต้องตรวจทั้ง UI, API, สิทธิ์, สถานะ, การแจ้งเตือน และเงื่อนไขยื่นซ้ำร่วมกัน การเปลี่ยนป้ายข้อความอย่างเดียวไม่ถือว่า flow เปลี่ยนแล้ว

## ข้อมูลคงค้างที่มีผลต่อการเปิดใช้งานจริง

1. **วันตัดรอบรายวิชา:** 1/3 ของ Block นับวันหรือสัปดาห์ ปัดอย่างไร “ก่อน Final 1 สัปดาห์” หมายถึงเส้นตายวันใด/เวลาใด และมีประกาศวันจริงของแต่ละ Section/Block หรือไม่ ใช้วันจริงตั้งค่าได้ก่อนสูตรอัตโนมัติ
2. **ขอบเขตและลำดับช่องทาง:** กรณีตัวอย่างยื่นสัปดาห์ 6 ทำ Reg เมื่อใด วิชาเต็มภาคเปิดช่วงใด และถอน Block 7–12 ต้องทำ Reg/รวมสองฉบับหรือไม่ ลำดับ Reg/PI ของแต่ละกรณีต้องระบุแยก
3. **ผู้มีอำนาจและเอกสาร:** ใครตรวจ ใครลงนาม ใครทำแทนได้ ไฟล์สองฉบับคืออะไร ต้องมีลายเซ็นใครบ้าง และชุดเอกสารแต่ละเส้นทางเหมือนกันหรือไม่ ระหว่างนี้พัฒนาคิว/รับไฟล์ได้โดยไม่สร้างแบบฟอร์มหรือลายเซ็นเอง
4. **เกณฑ์จบ:** เจ้าหน้าที่ติดตามเอกสารครบแล้วจบหน้าที่สาขาหรือยังต้องรอผลทะเบียน/สนท. ใครเป็นผู้ยืนยันและใช้หลักฐานอะไร

ข้อสงสัยเหล่านี้ไม่ใช่เหตุผลให้หยุดพัฒนาคิวตรวจ เอกสาร และหน้าติดตามทั้งหมด งานเชื่อมต่อ API/SSO/ระบบไฟล์และความพร้อมติดตั้งจริงยังเป็นงานทีมพัฒนาและผู้ดูแลระบบ ไม่ใช่รอคำตอบพี่นัทอย่างเดียว

## คัดข้อมูลอื่นที่แนบมาด้วย

- ค่าเทอม/คืนสถานภาพ: ยังไม่ระบุผลต่อสิทธิ์หรือเส้นตายลด/ถอน ดู [บันทึกแยก](REINSTATEMENT-2026-11-04.md) ไม่เพิ่มเงื่อนไขห้ามยื่นเอง
- จท41/CR41 หน่วยกิตเกินและลงทะเบียนสาย: กฎ 22/24 หน่วยกิตและ GPAX 3.25 เป็นเงื่อนไขลงทะเบียนตามข้อความ ไม่ใช่เกณฑ์ลด/ถอน และข้อความ “ยื่น CR41 แล้วไม่ต้องลงทะเบียน Reg Chula” ห้ามนำมาใช้ยกเว้นขั้น Reg ของคำร้องลด/ถอน
- การลงทะเบียนผ่านคำร้องภายนอกอาจทำให้ข้อมูลรายวิชาเปลี่ยนภายหลัง เป็นประเด็นความสดของข้อมูลที่ควรตรวจเมื่อเชื่อมข้อมูลจริง ยังไม่ใช่หลักฐานว่าสถานการณ์นี้เกิดขึ้นแล้วหรือเปลี่ยนสิทธิ์อย่างไร

## ผลงานรอบรับข้อมูลนี้

เทียบ requirement ใหม่กับโค้ด บันทึกเส้นทาง ช่องว่าง และลำดับพัฒนา พร้อมเชื่อมจากรายงานและคู่มือเดโม ยังไม่ได้เปลี่ยน backend flow ปฏิทิน ฐานข้อมูล หรือเพิ่มฟีเจอร์เอกสารในรอบนี้ และไม่ได้รันชุดทดสอบซ้ำเพราะแก้เอกสารเท่านั้น
