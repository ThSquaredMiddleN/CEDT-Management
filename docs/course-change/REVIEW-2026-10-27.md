# ผลตรวจ Auto Drop/Withdrawal Portal — 27 ตุลาคม 2569

> บันทึกนี้เป็นผลตรวจก่อนแก้ไข ดูสถานะงานที่แก้แล้วและผลทดสอบล่าสุดใน [IMPLEMENTATION-2026-10-27.md](IMPLEMENTATION-2026-10-27.md)

## ข้อสรุป

**มีแกนหลักของ working prototype ทั้งฝั่งนิสิตและเจ้าหน้าที่ แต่ยังไม่ครบตามระบบอัตโนมัติในโจทย์ และ UX/UI ยังต้องแก้ก่อนส่งมอบ**

ระบบเลือกเส้นทาง A/B/C ตามตารางที่ให้มาได้ มีการยื่นคำร้อง ตรวจสิทธิ์นิสิต ตรวจรายวิชา กันคำร้องซ้ำ อนุมัติ/ไม่อนุมัติ ยกเลิก และติดตามสถานะ แต่ยังไม่มีการเชื่อมมหาวิทยาลัยจริง ไม่มี PDF/ลายเซ็นดิจิทัลจริง ไม่มีหน้าตั้งค่านโยบาย และมีช่องว่างในสายอนุมัติ/ผลทะเบียน/การแสดงผลมือถือ

การประเมินนี้เทียบกับโจทย์ที่ผู้รับผิดชอบให้มาและโค้ดปัจจุบัน ไม่ใช่การรับรองระเบียบทะเบียนของมหาวิทยาลัย ไม่มี Figma URL สำหรับเทียบความตรงของงานออกแบบ

แนวทางที่เล็กและชัดที่สุดคือปิดข้อผิดพลาดของ prototype ก่อน แล้วแยก milestone การเชื่อมระบบจริง ไม่จำเป็นต้องเพิ่ม LIFF หรือเปลี่ยนสถาปัตยกรรมเพื่อแก้ปัญหา UI/flow ที่พบ

## ประเด็นที่ต้องแก้ เรียงตามความสำคัญ

### 1. [P1] สายอนุมัติ Flow B ไม่ตรวจความเป็นอาจารย์ที่ปรึกษา

**หลักฐาน:** `backend/src/modules/course-change/routes.ts:83` ตรวจ auth ระดับ admin; `backend/src/plugins/auth.ts:109` แปล admin เป็น staff ทุกคน; `backend/src/modules/course-change/service.ts:530` เปลี่ยนสถานะด้วย id/status โดยไม่ตรวจ snapshot.advisorId เทียบกับผู้อนุมัติ การแจ้งเตือนที่เลือก advisor ใน `service.ts:225` ไม่ใช่การบังคับสิทธิ์

**ผล:** staff คนอื่นสามารถอนุมัติ Flow B และชื่อคนนั้นจะถูกใช้ในช่องอาจารย์ที่ปรึกษาบนเอกสาร ทั้งที่ workflow อธิบายว่ารออาจารย์ที่ปรึกษา เรื่องนี้สอดคล้องกับ spec ภายในที่ให้ staff อนุมัติทั้งหมด แต่ไม่ละเอียดพอสำหรับสายอนุมัติในโจทย์

**แก้:** กำหนดบทบาทผู้พิจารณาแต่ละ flow ให้ชัด ตรวจสิทธิ์รายคำร้องทั้ง approve/reject/bulk และกำหนดสิทธิ์มอบหมายแทนอย่างชัดเจน แยกสิทธิ์บันทึกผลทะเบียนจากสิทธิ์ advisor หากเป็นคนละหน้าที่

### 2. [P1] Flow C แจ้งว่าส่ง สนท. ทั้งที่บันทึกเพียงประวัติ

**หลักฐาน:** `backend/src/modules/course-change/service.ts:572` ทำเพียง event `forwarded_to_registrar`; `:579` แจ้งนิสิตว่า “ระบบส่งต่อให้ทะเบียนอัตโนมัติ” ไม่มี adapter ส่ง สนท. ใน integrations

**ผล:** หน้าติดตามแสดงว่าหลักสูตรส่งต่อแล้วทั้งที่ไม่มีหลักฐานการส่งหรือการรับจริง

**แก้:** แยก “หลักสูตรอนุมัติแล้ว” กับ “ส่ง สนท. แล้ว” ให้เกิดคนละขั้น เพิ่มการรวบรวม/ส่งออกหรือ integration และบันทึกเลขอ้างอิงหลังการส่งสำเร็จ ระหว่างเป็น mock ให้ติดป้ายสาธิตชัดเจน

### 3. [P1] ผลทะเบียนมีเฉพาะสำเร็จ ไม่มีกรณีทะเบียนไม่อนุมัติ

**หลักฐาน:** `backend/src/modules/course-change/service.ts:647` รับเพียง note และเปลี่ยน processing → completed เสมอ; `frontend/src/features/course-change/StaffView.tsx` dialog บันทึกผลอธิบายว่าจะเปลี่ยนเป็นสำเร็จ ผู้ตรวจเปิด dialog ยืนยันได้จริง

**ผล:** กรณีหลักสูตรอนุมัติแต่ทะเบียนปฏิเสธไม่สามารถปิดคำร้องอย่างตรงความจริงได้ สถานะ rejected ปัจจุบันใช้ได้เฉพาะ pending_approval

**แก้:** เพิ่มผลทะเบียนสำเร็จ/ไม่สำเร็จ พร้อมเหตุผลและหลักฐานอ้างอิง แยกจากผลพิจารณาของหลักสูตร และกำหนดว่ายื่นใหม่ได้หรือไม่สำหรับแต่ละผล

### 4. [P1 สำหรับระบบจริง] ระบบภายนอก เอกสาร และตัวตนยังเป็น prototype

**หลักฐาน:** `backend/src/modules/course-change/integrations.ts:51` คืน ref ที่ประกอบจากเลขคำร้องและ delivered:true; `:72` เลือก mockIntegrations เสมอ; `document.ts:9` ระบุ HTML + hash; `document.ts:31` hash JSON; `routes.ts:112` ส่ง text/html ส่วน PI adapter รับเพียงเลขคำร้อง รหัสนิสิต และ hash (`integrations.ts:26`) ไม่มีไฟล์/ที่อยู่ไฟล์

**ผล:** ไม่มีการส่งข้อมูลจริง/อัปโหลดไฟล์จริง/ส่ง LINE จริง SHA-256 ไม่ใช่หลักฐานว่ามีการลงนามด้วย private key และยังไม่มี PDF ให้ระบบปลายทางรับ

**แก้:** เชื่อมบริการจริงเมื่อได้ API contract, สร้าง PDF ตามแบบที่ปลายทางรับ, ส่ง binary หรือ object reference พร้อม metadata, ทำการยืนยันผู้ลงนามตามข้อกำหนดที่หลักสูตรยืนยัน เพิ่ม webhook/poll รับผลและ outbox/retry/idempotency ก่อนใช้ network จริง ปัจจุบัน service เรียก integrations อยู่ใน DB transaction

### 5. [P1] Bulk approval ยังอนุมัติรายการที่ซ่อนจากแท็บปัจจุบันได้

**ทำซ้ำใน UI:** ในแท็บรออนุมัติ เลือก CR-2026-00025 → สลับไปกำลังดำเนินการ → ปุ่ม “อนุมัติที่เลือก (1)” ยัง enabled แต่รายการที่เลือกไม่อยู่ในหน้าจอ

**หลักฐาน:** `frontend/src/features/course-change/StaffView.tsx:78` สร้าง checkedIds จาก all ไม่ใช่ items ที่แสดง และ `:89` ส่งทันทีโดยไม่มีหน้าสรุปการยืนยัน

**ผล:** เจ้าหน้าที่เสี่ยงอนุมัติคำร้องที่ไม่ได้กำลังตรวจ โดย Flow B ยังสร้างเอกสารและส่งต่อทันที

**แก้:** จำกัด selection ตามรายการที่มองเห็น/ล้างเมื่อเปลี่ยนแท็บ หรือแสดงถาดรายการที่เลือกข้ามแท็บอย่างชัดเจน พร้อมยืนยันเลขคำร้องและผลที่จะเกิดก่อนส่ง แสดงข้อผิดพลาดรายรายการและเก็บรายการที่ล้มเหลวไว้ให้ลองใหม่ ปัจจุบัน `:94–95` แสดงแค่จำนวนแล้วล้าง selection ทั้งหมด

### 6. [P2] มือถือมี horizontal overflow และปุ่มทับสถานะ

### 8. [P2] Inbox ซ่อนรายการเก่าเมื่อเกิน 200 และตัวเลขสถานะอาจนับขาด

**ผล:** ถ้า 200 รายการล่าสุดเป็นคำร้องที่ปิดแล้ว คำร้องเก่าที่รออนุมัติอาจหายจาก inbox และตัวนับแสดงศูนย์ เจ้าหน้าที่ไม่มี pagination/search เพื่อค้นคืน

**แก้:** นำเข้ารายวิชาที่ลงทะเบียนจริงและประกาศรายประเภท/รายเทอม เพิ่มหน้าจัดการพร้อม preview/audit และ validation ช่วงเวลาทับซ้อน ไม่ควรนับ CRUD วิชาใน Master Data ว่าทดแทนหน้าตั้งค่า Course Change ครบแล้ว

### 11. [P2] รายละเอียดยืนยัน/ยกเลิกและความชัดเจนของข้อความยังไม่ครบ

## ประเด็นนโยบายที่ยังยืนยันว่า flow “เป๊ะ” ไม่ได้

1. โจทย์ส่วนกระบวนการเดิมระบุถอนสัปดาห์ 3–6 ว่ารอ Outlook แต่ส่วน automated workflow ระบุสัปดาห์ 1–6 ส่ง Reg Chula ตรง โค้ดเลือกอย่างหลัง ควรระบุให้แน่นอนว่านโยบายใหม่ยกเลิกการอนุมัติเดิมในช่วงนี้หรือไม่
2. ผู้อนุมัติ Flow C เป็นใคร และอาจารย์/เจ้าหน้าที่คนอื่นทำแทนกันได้เมื่อใด
3. วันตัดรอบใช้วันจริง/เวลาใด วันหยุดและสัปดาห์สอบนับอย่างไร ปัจจุบันบวกทีละ 7 วันจากวันเปิดเทอม หน้าเว็บวันที่ 27 ต.ค. 2569 แสดง week13 และปิด 6 ธ.ค. 2569 ขณะที่ README ระบุวันสิ้นเทอม 27 พ.ย. ต้องตัดสินว่า week18 รวมสอบหรือควรใช้ปฏิทินทะเบียน ไม่ควรแก้ด้วยการเดาวันเอง
4. Flow C ต้องสร้างคำร้อง/หลักฐานแนบหรือไม่ ปัจจุบัน UI บอกว่าเส้นทางนี้ไม่ต้องใช้เอกสาร
5. แบบเอกสาร ผู้ลงนาม ช่องทางส่ง และวิธียืนยันลายเซ็นที่ปลายทางยอมรับ

## ช่องว่างการทดสอบ

45 tests ผ่านเป็นหลักฐานว่าพฤติกรรมที่มี assertions ยังทำงาน แต่ไม่ใช่หลักฐานว่าครบโจทย์ทั้งหมด

- Flow B มี integration happy path ถึง completed
- Flow C integration ปัจจุบันทดสอบ submit/reject/retry/cancel ยังไม่ครอบคลุม approve → ส่งต่อ → completed
- Flow A มี unit routing แต่ไม่พบ integration submit → ส่ง Reg Chula → รับผลครบวงจรในชุดที่ตรวจ
- ยังไม่ครอบคลุม wrong-advisor authorization, bulk partial failure/ซ่อน selection, concurrent approvals/cancel race, รายการเกิน 200, ข้าม deadline ระหว่างเปิดหน้า และ external timeout/partial success/retry
- ควรเพิ่ม responsive/keyboard checks และ usability test จริงกับนิสิต/เจ้าหน้าที่

## เกณฑ์ปิดงานที่แนะนำ

**ก่อนปิด milestone prototype:** กำหนดผู้อนุมัติ/ผลทะเบียน, แก้ hidden bulk selection, แก้ mobile overflow และ keyboard menu, ทำข้อความ mock ให้ตรงความจริง, เพิ่ม tests ของ A/C และกรณีสำคัญที่ขาด แล้วทดสอบงานจริงกับตัวแทนทั้งสองบทบาท
