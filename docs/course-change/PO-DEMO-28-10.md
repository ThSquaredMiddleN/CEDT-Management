## จุดประสงค์ที่เราเสนอ

ให้นิสิตรู้ว่ายื่นได้หรือไม่ ต้องทำอะไรต่อ และรอใคร ส่วนเจ้าหน้าที่มีจุดรับคำร้อง ตรวจงาน และรวบรวมข้อมูลในที่เดียว ผลลดเวลาหรือลดการตามงานจริงยังต้องวัดกับพี่นัทและนิสิต

สถานะปัจจุบัน: การยื่น พิจารณา ติดตาม และตั้งค่าทำงานกับฐานข้อมูลของเดโมจริง ส่วนการยืนยันตัวตนและข้อมูลลงทะเบียนมหาวิทยาลัย การส่งทะเบียน/PI/LINE และเอกสารทางการยังไม่เชื่อมจริง

## สคริปต์สาธิตประมาณ 8–10 นาที

ใช้บัญชีทดสอบใน README; สลับบัญชีด้วยออกจากระบบ ระวังไม่อนุมัติรายการอื่นนอกตัวอย่างที่ตั้งใจใช้ การสาธิตจะเปลี่ยนสถานะข้อมูลเดโมจริง

| ลำดับ | ทำบนหน้าจอ | สิ่งที่ให้ PO เห็น |
|---|---|---|
| 1. นิสิตเริ่มคำร้อง | เข้าเป็น student3 เลือกลด/ถอน ดูกำหนดเวลา ค้นหาวิชา และอ่านเหตุผลของวิชาที่ทำรายการไม่ได้ | เราเสนอให้ระบบช่วยตรวจสิทธิ์และเวลา แทนการให้นิสิตไล่อ่านหลายประกาศ |
| 2. กรอกแล้วกลับมา | เลือกวิชาที่ยังไม่มีคำร้องที่มีผล กรอกเหตุผล รีโหลดแท็บเดิม แล้วเปิดตรวจทาน | ฉบับร่างกลับมาครบ ยังไม่ยื่นเอง ผู้ใช้ตรวจวิชา/เหตุผล/เส้นทางก่อนยืนยัน |
| 3. ยื่นคำร้อง | ยืนยัน เก็บเลขคำร้อง แล้วเปิดติดตาม | คำร้องถูกบันทึกจริงในเดโม เห็นสถานะ ประวัติ และขั้นตอนถัดไป |
| 4. เจ้าหน้าที่ทำงาน | ออกจากระบบ เข้า admin ค้นเลขคำร้องหรือกรองวิชา/เทอม ตรวจรายละเอียด แล้วอนุมัติ | คำร้องชุดเดียวกันส่งต่อจากนิสิตมาถึงเจ้าหน้าที่ สถานะขยับแต่ยังไม่ถือว่าทะเบียนสำเร็จ |
| 5. นิสิตเห็นความคืบหน้า | กลับเข้าบัญชีนิสิต เปิดคำร้องเดิม กดอัปเดตหากยังไม่เห็น (ปกติตรวจใหม่ทุก 30 วินาที) | ผู้ใช้ไม่ต้องเดาว่างานหายหรือค้างขั้นตอนไหน |
| 6. ลดงานรวบรวม | กลับเป็นเจ้าหน้าที่ เลือกคำร้องที่รอพิจารณา ดูหน้าตรวจทานอนุมัติกลุ่มและส่งออกสรุป CSV | รวมงานตามวิชา/เทอมได้ ไฟล์สรุปไม่ใช่คำร้องทางการ; ปิดหน้าตรวจทานได้โดยไม่ต้องอนุมัติจริง |
| 7. กรณีไม่อนุมัติ | ใช้อีกคำร้องตัวอย่าง กรอกเหตุผลไม่อนุมัติ แล้วให้นิสิตดูเหตุผลและประวัติ | เราเสนอให้ผลไม่อนุมัติมีเหตุผลและตรวจสอบย้อนหลังได้ การยื่นใหม่ต้องตรวจสิทธิ์/เวลาใหม่ |
| 8. การตั้งค่า | เปิดตั้งค่า ดูประกาศรายวิชาและกำหนดช่วงเวลา ลองเพิ่มช่วงที่ทับกัน แล้วทิ้งการแก้ไข | เจ้าหน้าที่ปรับกฎผ่านหน้าจอได้ มี validation, ยืนยันและประวัติการแก้ไข; กฎที่เห็นเป็นเดโม ไม่ใช่ระเบียบที่ยืนยันแล้ว |

ถ้าจะแสดงผลสำเร็จ ให้เจ้าหน้าที่กด “บันทึกผลจากทะเบียน” หลังอนุมัติ พร้อมบอกว่าเป็นการบันทึกผลในเดโมด้วยมือ ไม่ได้รับผลจริงจากทะเบียน

วันที่ 28/10/2569 เดโมอยู่สัปดาห์ที่ 13 คำร้องใหม่ตามกฎตัวอย่างจะผ่านหลักสูตร การแสดงเอกสารตัวอย่างให้เปิดคำร้องเก่าที่มีเอกสาร หรือใช้กรณี Flow B ที่เตรียมไว้ อย่าอธิบายว่า Flow B คือกฎของคำร้องใหม่วันนี้ และอย่าปรับวันจำลองระหว่างเล่าโดยไม่แจ้งผู้ชม

ส่วนเสริมเมื่อมีเวลา: ยกเลิกคำร้องที่ยังรอพิจารณา; เปิดแจ้งเตือนตรงคำร้อง; แสดงมือถือ; ทดสอบขัดข้องในเครื่องทดสอบแล้วใช้ตรวจผลการยื่นก่อนลองใหม่

## สิ่งที่ยังเล่นเป็น flow จริงไม่ได้

| เรื่อง | สถานะปัจจุบัน | แผนที่เราเสนอ |
|---|---|---|
| Block / วิชาเลือกแต่ละช่วง | ยังใช้ตารางระดับเทอม ไม่มีการผูกกฎราย Block/ครึ่งเทอมที่ยืนยันแล้ว | เสนอตารางกฎแยกรูปแบบวิชา ให้หลักสูตรยืนยันรายวิชาและเส้นตาย |
| รวบรวมให้อาจารย์ลงนาม → คืนเอกสาร → นิสิตทำ Reg Chula → รวม 2 ฉบับ → ส่ง PI | ยังไม่มีชุดสถานะและหน้าจอจัดการเอกสารครบเส้นทางนี้ | เราออกแบบลำดับงานและผู้รับผิดชอบเป็นข้อเสนอ แล้วใช้ตัวอย่างจริงตรวจความถูกต้อง |
| PDF ทางการ / รวมไฟล์จริง / ลายเซ็น | มี HTML ตัวอย่างในบางเส้นทาง ไม่ใช่ PDF ที่หน่วยงานรับรอง | กำหนดการรับไฟล์ ตรวจความครบ รวมเอกสาร และหลักฐาน ตามแบบ/ข้อกำหนดที่ยืนยัน |
| SSO / ลงทะเบียน / Reg Chula / PI / LINE หรือ email จริง | Login ท้องถิ่น ข้อมูลลงทะเบียนสังเคราะห์ การส่งภายนอกเป็น mock; ไม่มี email จริง | ขอ API contract และสิทธิ์จากผู้ดูแลแต่ละระบบ; ไม่ถือว่าการจำลองส่งสำเร็จเป็นหลักฐานการเชื่อมต่อ |
| บทบาทอาจารย์/เจ้าหน้าที่และการมอบหมาย | ใช้ staff ร่วมกัน ยังไม่แยกสิทธิ์ตามขั้นตอนจริงครบ | เราเสนอสิทธิ์ตามงาน ให้หลักสูตรยืนยันผู้มีอำนาจและการทำแทน |
| ความพร้อมใช้งานจริง | ยังไม่มีคิวส่งภายนอก/การลองส่งใหม่ครบ และยังไม่ตรวจระบบติดตั้งจริง/UAT ครบ | งานเทคนิคเป็นความรับผิดชอบทีมพัฒนา แยกจากคำถามที่รอพี่นัท |

## Requirement ที่เราควรนำเสนอเอง

ข้อเสนอต่อไปนี้ยังไม่ใช่ฟีเจอร์ที่ทำครบหรือข้อตกลงที่ PO อนุมัติแล้ว

**รุ่นแรกที่เสนอ:** ศูนย์กลางรับคำร้อง รวบรวมงาน ติดตาม และช่วยจัดการเอกสาร โดยยังรองรับขั้นตอนที่นิสิต/เจ้าหน้าที่ต้องทำในระบบภายนอกเอง จบแต่ละขั้นเมื่อมีผู้รับผิดชอบบันทึกผลและหลักฐานตามที่ยืนยัน การส่งอัตโนมัติจริงเพิ่มเมื่อมีช่องทางรองรับ

ลำดับงานสำหรับกรณี Block ที่เสนอให้ PO ดู:

1. นิสิตยื่นคำร้องหลักสูตรและเห็นรายการสิ่งที่ต้องเตรียม
2. เจ้าหน้าที่รวบรวมตามวิชา/รอบ ส่งให้ผู้ลงนาม และคืนฉบับที่ลงนามแล้วในคำร้องเดิม
3. ระบบแจ้งนิสิตว่าต้องดำเนินการใน Reg Chula พร้อมรายการขั้นตอนที่ตรงกับวิชานั้น
4. นิสิตนำเอกสารจาก Reg Chula กลับมา ระบบตรวจว่าครบสองฉบับและช่วยรวมไฟล์
5. ส่ง PI ผ่านช่องทางที่ได้รับอนุญาต หรือให้นิสิตทำพร้อมบันทึกหลักฐาน หากยังไม่มีการเชื่อมต่อ
6. ติดตามจนได้รับผลสุดท้าย โดยแยกการอนุมัติ การส่ง และผลทะเบียนออกจากกัน

สิ่งที่เราตัดสินใจออกแบบ/เสนอเองได้: ลำดับหน้าจอ ข้อความ การค้นหา/รวบรวม การบอกผู้ทำขั้นตอนถัดไป การตรวจความครบ ฉบับร่าง การกู้คืน และการยืนยันก่อนทำรายการ

สิ่งที่ต้องตรวจข้อเท็จจริง: วันตัดรอบ รายวิชาที่อยู่ในแต่ละรูปแบบ ผู้มีอำนาจลงนาม แบบเอกสารที่ยอมรับ และสิ่งที่ถือเป็นผลสุดท้าย ส่วน API/สิทธิ์/วิธีเชื่อมต่อให้ตรวจจากผู้ดูแลระบบนั้น

## ข้อสรุปที่ต้องการจากการคุยกับ PO

- เห็นด้วยหรือไม่ว่ารุ่นแรกควรแก้ “การรวบรวมและติดตาม” ก่อน พร้อมขั้นตอนเชื่อมต่อด้วยคนเมื่อยังไม่มี API
- ใช้กรณี Block สัปดาห์ 1–7 เป็นกรณีแรกที่จะพัฒนา flow เอกสารครบหรือไม่
- ยอมรับขอบเขตที่ยังเป็นการจำลอง และช่วยระบุผู้ประสานงานยืนยันกฎ/เอกสาร/ระบบปลายทาง

ไม่ใช้คำว่า “ระบบจริงเสร็จ รอแค่ข้อมูล” เพราะ flow เอกสารเฉพาะและงานเตรียมใช้งานจริงยังต้องพัฒนาและทดสอบต่อ ดู [rport 28/10](rport-28-10.md) และ [ชุดทดลองผู้ใช้](UAT-28-10.md)
